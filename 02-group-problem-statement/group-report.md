**Vì sao chọn — 4 lý do theo thứ tự quan trọng:**

```text
1. Card duy nhất có ground truth. Diff là sự thật tuyệt đối — AI nói "Hoàng sửa module auth tuần này" thì mở diff ra kiểm đúng/sai ngay. Các card khác (ôn thi, đọc paper) không có cách chấm khách quan.

2. Có thể lấy bằng chứng pain ngay hôm nay. Repo đồ án đã có sẵn lịch sử. Chạy `git shortlog -sn` + `git log --pretty=%s | grep -icE "^(update|fix|done|wip)$"` là ra % message vô nghĩa trên tổng commit — pain chứng minh bằng dữ liệu, không phải lời kể.

3. Có thể tạo tập test từ quá khứ. Lấy 4 tuần commit đã qua, tự tổng hợp thủ công làm đáp án, rồi chấm AI trên đó. Chạy 10-15 lần thử nghiệm trong 2 ngày, không phải chờ 8 tuần.

4. Input đã sạch và máy đọc được. `git log`, `git diff`, `--numstat` đều là dữ liệu có cấu trúc. Không có .docx, không có chat Zalo, không cần xin phép dữ liệu người khác.
```

**Vì sao KHÔNG chọn các candidate còn lại (mỗi bài 2-3 câu):**

```text

Mở 10 commit ngẫu nhiên: chỉ 3/10 hiểu được nội dung từ message | Hoàng nói "tao nhớ hết mình làm gì" — nhưng khi hỏi "tuần 5 ai sửa module auth?" thì phải mở diff 3 phút mới trả lời được | Pain không phải "commit message tệ" (đó là rule problem). Pain thật là "từ 200+ commit đã viết ẩu, cần rút ra ai đã thay đổi gì ở module nào, mà không có cách nào ngoài đọc diff thủ công" |

**Insight sau validation (1-2 câu — pain thật nằm ở đâu):**

```text
Pain thật không nằm ở "commit message viết tệ" — đó là vấn đề rule, áp convention là xong. Pain nằm ở: (a) 200+ commit đã lỡ viết ẩu trong quá khứ không sửa lại được, và (b) kể cả message tốt cũng không chứa thông tin "thay đổi gì ở module nào" — phải đọc diff mới biết. Đây là task AI giỏi: đọc diff → suy ra ngữ nghĩa → gom theo người/module.
```

**Research takeaway (2-3 câu — nên build gì / không build gì):**

```text
Không nên build tool mới. Hướng hợp lý: (1) Rule (convention prefix) áp cho commit từ giờ → git-cliff tạo changelog tự động. (2) AI Workflow cho commit đã qua: `git log --numstat` + `git diff` → feed vào ChatGPT/Claude với prompt chuẩn → AI tổng hợp theo người/module → trưởng nhóm review. Pattern: dữ liệu có cấu trúc (diff) + AI suy ngữ nghĩa + con người verify bằng cách mở diff gốc.
```

> Lưu ý: không dùng số liệu AI đưa nếu không verify được link chính thức. Ghi rõ giả định chưa chắc.

**Bottleneck chính (2-3 câu):**

```text
Bước 3 là bottleneck rõ nhất: trưởng nhóm phải mở từng commit, đọc diff (code thêm/xoá), suy ra ngữ nghĩa ("đây là fix login bug" hay "refactor database query"), rồi gom lại theo module. Với 43% commit message vô nghĩa, không thể dựa vào message — phải đọc diff thật. Bước này mất 45-60 phút, chiếm >50% tổng thời gian, vì đòi hỏi hiểu code + suy ngữ nghĩa. Đây đúng là task AI làm tốt: đọc diff có cấu trúc, suy ra thay đổi ngữ nghĩa, gom theo module.
```

### 5.2. Future workflow bản nhóm

Phải nhìn ra 5 thứ: bước nào máy (Rule), bước nào AI, bước nào người, boundary ở đâu, fallback khi AI sai.

```text
FUTURE STATE — Tổng hợp đóng góp từ commit history — dưới 5 phút (Agent tự chạy)

[1 Trưởng nhóm trigger Agent (nhập repo URL + khoảng thời gian): 1' - Trưởng nhóm]
→ [2 Agent tự clone/pull repo, chạy `git log --numstat`, `git diff`, phân tích cấu trúc project: 1' - Agent]
→ [3 Agent tự chia batch theo tuần, đọc diff từng batch, suy ngữ nghĩa, phát hiện module từ cấu trúc thư mục: 2' - Agent]
→ [4 Agent tổng hợp bản báo cáo theo người + module + tuần, trích commit hash, tạo bảng Markdown: 1' - Agent]
→ [5 Trưởng nhóm review bản tổng hợp: spot-check 3-5 dòng bằng cách click commit hash: 5' - Trưởng nhóm]  <-- human boundary

Tại sao Agent chứ không phải Workflow:
- Workflow yêu cầu trưởng nhóm tự export, tự chia batch, tự paste vào ChatGPT, tự gom output — vẫn tốn 15-20 phút thao tác thủ công.
- Agent tự làm toàn bộ pipeline: clone → phân tích → chia batch → đọc diff → gom → tạo báo cáo. Trưởng nhóm chỉ cần trigger và review output.
- Sự khác biệt rõ ràng: Workflow giảm từ 90' → 20' (tiết kiệm 70'). Agent giảm từ 90' → 5' (tiết kiệm 85'). Agent can thiệp sâu hơn, tạo ra output hoàn chỉnh hơn.

Fallback:
- Agent suy sai ngữ nghĩa diff → Trưởng nhóm click commit hash trong báo cáo để verify, sửa tay.
- Agent bỏ sót commit → Cross-check tổng commit trong output vs `git shortlog -sn` (phải khớp).
- Agent không truy cập được repo (private/permission) → Trưởng nhóm export `git log` thủ công, feed vào Agent.
- Output quá dài/lộn xộn → Agent retry với scope hẹp hơn (1 tuần thay vì 1 tháng).

Rule song song:
- Từ giờ trở đi: áp convention `feat/fix/docs: <mô tả>` → git-cliff changelog tự động.
- Agent xử lý cả commit quá khứ (message ẩu) lẫn phân loại theo module (message dù tốt cũng không chứa).
```

**Before/after impact:**

| Metric | Trước | Sau kỳ vọng | Cách đo |
|---|---:|---:|---|
| Tổng thời gian | 90-120 phút/lần | dưới 5 phút/lần | Bấm giờ trên 2 sprint/tuần |
| Thao tác thủ công trưởng nhóm | 5 bước, 90-120 phút | 2 bước (trigger + review), 6 phút | Đếm bước + thời gian |

| Độ chính xác | 100% (tự đọc) nhưng mất thời gian | ≥90% dòng kiểm chứng ngược về commit cụ thể | Spot-check 20 dòng ngẫu nhiên |
| Risk mới | Không có AI risk | Agent suy sai ngữ nghĩa, bỏ sót commit | Số dòng phải sửa + số commit bị sót |

## Phase 6 — Rule / Workflow / Agent + Decision

### 6.0. Ma trận độ phù hợp

- Độ mơ hồ: [ ] Thấp — Vì sao: Output (bản tổng hợp đóng góp) có ground truth: mở diff ra kiểm đúng/sai. Không phải "nhiều cách đều OK".
- Độ phức tạp: [x] Trung bình — Vì sao: Tuy input có cấu trúc, nhưng pipeline có nhiều bước cần phối hợp (clone repo → phân tích cấu trúc project → chia batch → đọc diff → suy ngữ nghĩa → gom theo module → tạo báo cáo). Nếu để người làm từng bước (Workflow), vẫn tốn 15-20 phút thao tác. Agent tự phối hợp các bước này hiệu quả hơn.

**Bài toán nhóm nằm ở ô nào:**

```text
Độ mơ hồ thấp + Độ phức tạp trung bình → "Agent tự lập kế hoạch pipeline, con người chỉ trigger và review"
```

**Vì sao (2-3 câu):**

```text
Bài toán có ground truth (diff kiểm chứng được) nên rủi ro AI sai được kiểm soát. Nhưng pipeline có 5-6 bước phối hợp (clone → phân tích → chia batch → đọc → gom → viết báo cáo) — nếu dùng Workflow, trưởng nhóm vẫn phải tự orchestrate từng bước (export, paste, gom output), mất 15-20 phút thao tác thủ công. Agent tự phối hợp toàn bộ pipeline, trưởng nhóm chỉ trigger + review, giảm xuống 5 phút — tạo ra sự khác biệt rõ ràng so với làm tay.
```

### 6.1. So sánh Rule / Workflow / Agent (so trên cùng 1 bài)

**5 câu hỏi chốt (trả lời câu đầy đủ):**
1. Rule có giải được 70-80% case không? → Không. Convention chỉ giải cho commit từ giờ. 200 commit quá khứ + phân loại theo module vẫn phải đọc diff. Rule giải được ~20%.
2. Các bước có đi thẳng một đường không hay phải phối hợp? → Có 5-6 bước cần phối hợp: clone → phân tích structure → chia batch → đọc diff → gom → viết báo cáo. Nếu Workflow, trưởng nhóm tự orchestrate mất 15-20 phút. Agent tự làm pipeline trong 2-3 phút.
3. Có thật sự cần Agent tự lập kế hoạch + gọi tool không? → **Có.** Agent cần: (a) tự phân tích cấu trúc project để biết module nào ở thư mục nào, (b) tự chia batch thông minh theo tuần/theo người để không vượt context window, (c) tự gom output nhiều batch thành 1 báo cáo thống nhất. Workflow không làm được các bước phối hợp này.
4. Nếu AI sai, ai phát hiện đầu tiên và sửa trong bao lâu? → Trưởng nhóm click commit hash trong báo cáo → mở diff gốc verify. 30 giây/dòng. Ground truth có sẵn nên phát hiện sai rất nhanh. Hậu quả: sửa trước nộp báo cáo.
5. Có hạ được từ Agent → Workflow → Rule không? → Đã thử: Workflow vẫn tốn 15-20 phút thao tác thủ công (export, paste, gom), can thiệp chưa sâu, khác biệt không rõ ràng. Agent giảm xuống 5 phút, sự khác biệt so với làm tay là **18x** (90 phút → 5 phút). Rule chỉ giải tương lai, không đủ.

**Mức chọn:**

```text

```

**Vì sao chọn (3-4 câu):**

```text

(2) Ground truth (diff) giúp kiểm soát rủi ro Agent sai — trưởng nhóm click commit hash verify trong 30 giây. (3) Sự khác biệt rõ ràng: Workflow giảm từ 90' → 20' (4.5x), Agent giảm từ 90' → 5' (18x). (4) Input có cấu trúc (git log/diff) nên Agent đọc tốt, không cần xử lý dữ liệu bẩn.
```

**Vì sao không chọn mức đơn giản hơn (2-3 câu):**

```text

Workflow giải được bottleneck nhưng trưởng nhóm vẫn phải tự orchestrate pipeline (export, chia batch, paste, gom output) — mất 15-20 phút, can thiệp chưa sâu, khác biệt không đủ rõ so với làm tay.
